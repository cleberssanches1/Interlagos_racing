Plano de Cápsula 2D para Colisão de Carro no Saturn

Objetivo

Evoluir a colisão do carro para um volume proxy mais correto do que um ponto central, usando uma cápsula 2D no plano XZ, mas sem repetir o erro das tentativas anteriores que deixaram a aplicação pesada o suficiente para não subir no emulador.

Diagnóstico consolidado

ItemResultadoConclusão
Multi-probe no GroundFollower Quebra o runtime Não podemos aumentar o número de queries por frame no caminho low-cost.
Histerese / wall latch no GroundFollower Quebra o runtime Também não podemos adicionar estado e lógica extra nesse hot path.
Solver mais sofisticado dentro de FindPlanarWallPush Quebra o runtime O solver atual está no limite estrutural aceitável.
Colisão atual com 1 query e cache WallSegment2D Sobe no emulador Este é o baseline seguro.
Tuning de constantes Seguro É o único tipo de mudança runtime que hoje temos evidência de estabilidade.

Conclusão técnica

A cápsula 2D continua sendo a melhor forma geométrica para representar o carro no plano XZ. O problema não é a forma; o problema é o custo de resolver essa forma dentro do runtime atual do Saturn. Portanto, a implantação deve ser feita em fases. Primeiro consolidamos dados e preparação offline. Só depois tentamos um runtime mínimo.

Modelo geométrico alvo

Representação do carro:

capsule = segment(frontCenter, rearCenter) + radius

Representação da parede:

wall = 1 segmento 2D orientado no XZ, vindo do cache WallSegment2D

Solver ideal:

distance(capsuleSegment, wallSegment) -> if distance < radius, compute push vector

Por que a cápsula é melhor que a caixa

FormaVantagemDesvantagem
Caixa 2D Mais simples de imaginar Quinas artificiais, contato seco, sensação visual ruim
Cápsula 2D Melhor aproximação de para-choque/laterais, entrada oblíqua mais natural Solver mais caro se implementado sem cuidado

Classes e pontos de código impactados

  • src/track_system.hpp: cache WallSegment2D
  • src/track_system.cxx: EnsureWallSegmentCache(...) e FindPlanarWallPush(...)
  • src/car_ground_follower.hpp: chamada única para ResolvePlanarWallPush(...)
  • src/car_physics_shared.hpp: constantes de raio, correção planar e damping pós-impacto

Plano em fases

Fase 0 - Baseline estável

Não alterar a topologia do runtime. Manter:

  • 1 query de parede por frame
  • solver atual no cache WallSegment2D
  • sem multi-probe
  • sem wall latch
  • sem solver novo dentro do hot path

Fase 1 - Preparação offline

Objetivo: melhorar a qualidade dos dados sem custo de runtime.

  • validar se cada WallSegment2D representa a melhor aresta vertical da face
  • remover duplicatas e segmentos degenerados
  • registrar largura/comprimento médio dos muros problemáticos
  • classificar paredes problemáticas por segmento da pista

Seguro: não mexe no loop de física.

Fase 2 - Especificação da cápsula fora do runtime

Objetivo: fechar as dimensões do proxy do carro sem alterar o jogo.

  • definir capsuleHalfLength
  • definir capsuleRadius
  • desenhar o alinhamento com o carro visual
  • calcular margens aceitáveis entre mesh visual e proxy invisível

Saída esperada:

frontCenter = carPos + forward * halfLength
rearCenter  = carPos - forward * halfLength
radius      = tuned constant

Fase 3 - Shadow mode

Objetivo: calcular a cápsula 2D em modo sombra, sem aplicá-la na física do jogo.

  • rodar solver de cápsula apenas como diagnóstico
  • não alterar outPush real
  • comparar o resultado do solver sombra com o solver atual
  • fazer isso sob flag de compilação, desativada por padrão

Só vale tentar se a instrumentação for mínima e comprovadamente não derrubar o runtime.

Fase 4 - Runtime mínimo experimental

Se a fase 3 for segura, substituir o solver atual por uma versão mínima da cápsula, com as seguintes restrições:

  • 1 query por frame continua obrigatório
  • usar apenas o cache WallSegment2D
  • sem fallback extra além do já existente
  • sem passes adicionais
  • sem latches

Se a aplicação voltar a não subir, abortar e retornar ao baseline imediatamente.

O que não fazer

  • não adicionar múltiplos pontos de contato no GroundFollower
  • não criar mais queries por frame
  • não adicionar estados temporais na colisão do carro
  • não introduzir solver com várias divisões/int64 extras no hot path sem shadow mode antes

Estratégia segura de curto prazo

Enquanto a cápsula 2D não é viável em runtime, a melhoria segura continua sendo:

  • tuning de kWallCollisionRadius
  • tuning de kMaxPlanarCorrectionPerFrame
  • tuning de kWallImpactForwardDamping
  • tuning de kWallImpactYawDamping
  • melhoria offline do cache de segmentos de parede

Critério de sucesso

  • o jogo continua abrindo no emulador
  • o carro não atravessa faces em contato frontal contínuo
  • ataques oblíquos passam a ser mais estáveis
  • o custo por frame não aumenta a ponto de derrubar o runtime

Recomendação final

A cápsula 2D continua sendo o destino técnico correto. Mas o próximo passo certo não é implementar mais runtime agora. O próximo passo certo é preparar a cápsula como modelo de referência e atacar primeiro os dados offline e o tuning do solver atual. Só depois disso vale uma nova tentativa controlada no hot path.
